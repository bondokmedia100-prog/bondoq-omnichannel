# نظام حلواني بندق متعدد القنوات

نقطة انطلاق عملية لمنصة دعم ومبيعات عربية RTL: واجهة Next.js، API بـ Express وTypeScript، PostgreSQL/Prisma، Redis/BullMQ، وSocket.IO للتحديثات الفورية.

## التشغيل باستخدام Docker

1. انسخ `.env.example` إلى `.env` وغيّر كلمات مرور الحسابات التجريبية و`JWT_SECRET` و`POSTGRES_PASSWORD` قبل أي نشر حقيقي.
2. من هذا المجلد شغّل `docker compose up --build`.
3. افتح `http://localhost:3000`.

عناوين الخدمة: الواجهة `http://localhost:3000`، الـ API `http://localhost:4000/api/health`، وWebhook واتساب على `/webhooks/kalemlywa` وMessenger على `/webhooks/meta`.

### التشغيل على Windows

1. ثبّت Docker Desktop لويندوز، وافتحه وانتظر حتى تظهر حالة التشغيل. يتطلب Docker Desktop تفعيل WSL 2 عادةً.
2. فك ضغط الحزمة إلى مجلد على الجهاز.
3. انقر مرتين على `START-WINDOWS.bat` وانتظر اكتمال البناء في المرة الأولى؛ يلزم اتصال بالإنترنت لتنزيل صور Docker.
4. ستفتح لوحة النظام في المتصفح على `http://localhost:3000`.
5. لإيقاف النظام مع الاحتفاظ ببياناته، انقر مرتين على `STOP-WINDOWS.bat`. لا تحذف مجلد Docker أو وحدات البيانات إذا أردت الاحتفاظ بالمحادثات.

لا يحتاج التشغيل المحلي إلى تثبيت Node.js أو PostgreSQL أو Redis على Windows؛ تشغّلها Docker Desktop داخل الحاويات. بيانات الدخول التجريبية المحلية موجودة أدناه، وهي للاختبار فقط. ربط WhatsApp الفعلي يتطلب إعداد بيانات المزود وعنوان Webhook عام؛ `localhost` وحده لا يستقبل Webhooks من الإنترنت.

المعاينة التفاعلية المنفصلة نموذج بصري ببيانات تجريبية، ولا تتصل بواجهة API أو تدخل ضمن خدمات النشر.

## حسابات التجربة

- المدير: `admin@bondoq.com` / `BondoqAdmin@2026`
- أحمد: `ahmed@bondoq.com` / `Agent@123`
- سارة: `sara@bondoq.com` / `Agent@123`
- محمود: `mahmoud@bondoq.com` / `Agent@123`
- الجودة: `quality@bondoq.com` / `Quality@123`

الحسابات التجريبية تُنشأ في `prisma/seed.ts`. غيّر كلمات مرور التجربة فورًا، ولا تستخدمها خارج بيئة محلية. كلمات المرور تُخزّن باستخدام bcrypt، ورمز JWT تجريبيًا صالح 12 ساعة.

## تطوير محلي دون Docker

1. شغّل PostgreSQL وRedis، واضبط `DATABASE_URL` و`REDIS_URL` في بيئة API.
2. داخل `apps/api`: نفّذ `npm install` ثم `npm run db:generate` و`npm run db:push` و`npm run db:seed` ثم `npm run dev`.
3. داخل `apps/web`: نفّذ `npm install` ثم `npm run dev`.

## قنوات الرسائل

- WhatsApp يرسل عبر KalemlyWA إلى `https://whatsapp.kalemly.com/api/send-message`، وتُستقبل الرسائل عبر `POST /webhooks/kalemlywa`. دليل Kalemly يوضح أن الأحداث تُرسل كطلب POST بجسم JSON ولا يوفر خانة لترويسة مصادقة؛ لوحة المدير تنسخ رابط استقبال كاملًا يتضمن `?token=`. الصق الرابط كاملًا في إعداد تطبيق Kalemly، ولا تحذف الرمز أو تشاركه علنًا.
- إعداد KalemlyWA متاح للمدير من زر «إعداد واتساب». يدخل المدير authkey وappkey كلًّا على حدة، ويُخزّنان مشفّرين. لا يحتاج API إلى Instance ID؛ وحمولة QR اختيارية وتُنسخ من KalemlyWA عند الحاجة.
- حفظ المفتاحين لا يرسل رسالة؛ اختبار الإرسال إجراء منفصل.
- إعداد Messenger متاح للمدير من زر «إعداد Messenger»؛ تُخزّن مفاتيح الصفحة وMeta مشفّرة ويمكن اختبار Page Access Token من الواجهة. سجّل `GET/POST /webhooks/meta` لدى Meta مع اشتراك أحداث الرسائل، وتظل نافذة الـ24 ساعة خاصة بـ Messenger.
- إعداد Telegram متاح للمدير من زر «إعداد Telegram»؛ تُخزّن بيانات البوت مشفّرة، ويمكن اختبارها وتسجيل `POST /webhooks/telegram` تلقائيًا باستخدام رمز حماية Webhook.
- الإرسال الصادر للنصوص والصور والصوت والموقع مهيأ في `apps/api/src/providers.ts`. يمكن للموظف رفع الصور والصوت وملفات PDF/Office/TXT (حتى 12 ميجابايت للملف) أو تسجيل رسالة صوتية. تُخزّن الملفات في PostgreSQL وتُقدّم عبر روابط موقعة؛ يتطلب الإرسال الفعلي عنوان API عامًا عبر `API_PUBLIC_URL`.
- رسائل WhatsApp الصادرة تمر عبر قائمة BullMQ بمحدد معدل وتأخير قصير. تظل ردود Messenger وإرسال المنتجات عبر Messenger مقفلة بعد نافذة Meta ذات 24 ساعة؛ لا تُطبق هذه النافذة على WhatsApp أو Telegram.
- رسالة البداية التفاعلية توجّه طلبات الدليفري والتورتات والشكاوى إلى أقسامها. عيّن موظفًا نشطًا لقسم الجودة أو ستبقى شكاوى الجودة في الطابور.
- نموذج المنتجات التجريبي يعبأ عبر `prisma/seed.ts`؛ استبدل الصور والأسعار التجريبية ببيانات العلامة من لوحة «كتالوج المنتجات». يمكن تحميل صورة المنتج أو استخدام رابط HTTPS عام.
- يمكن للمدير إضافة المنتجات وتعديل الاسم والقسم والسعر والوصف والصورة، أو إيقاف توفر الصنف. تُرسل تفاصيل المنتج والصورة كرسالتين لضمان وصول الاسم والسعر والوصف حتى إن لم تدعم القناة تعليق الصورة.
- عند اختيار «تم الحل»، يرسل النظام استبيان 1–5 ويحفظ الرد النصي الوارد في المحادثة (بالأرقام العربية أو اللاتينية). إشعار مراحل الطلب يستخدم القناة الأصلية؛ Messenger لا يتلقى إشعارًا خارج نافذته.
- تفريغ الرسائل الصوتية اختياري: اضبط `OPENAI_API_KEY`، ويُرسل النظام الصوت الوارد (حتى 25 MB) إلى نموذج `OPENAI_TRANSCRIPTION_MODEL` الافتراضي `whisper-1`. لا يُفعّل التفريغ عند ترك المفتاح فارغًا.
- بيانات دخول KalemlyWA وMeta وTelegram، عنوان HTTPS العام، الأسرار وإعدادات الأعمال يجب أن توفرها إدارة العلامة. لا يحتوي هذا المشروع على مفاتيح حقيقية.

## ما يتضمنه النموذج

- تسجيل دخول JWT، أدوار مدير النظام وقائد الفريق والموظف ومستخدم الفرع، وصلاحيات فردية لعرض المحادثات وتحويلها وإدارة الكتالوج والتقارير والفريق.
- إدارة المقر وموظفي العمل من المنزل والفروع الثمانية بأسماء قابلة للتعديل، مع توزيع الموظفين المتاحين وفق أقل حمل وتدوير عادل عند التعادل.
- حضور الموظف وتسجيل جلسات العمل، شاشة إشراف مباشرة، طابور انتظار، تنبيه SLA بعد 5 دقائق، تنبيه صوتي اختياري للرسائل الواردة، ومزامنة بعد عودة اتصال Socket.IO.
- همسات داخلية لا تُرسل لقنوات العملاء، تحويل المحادثات، سجل تدقيق، ردود جاهزة، وتسجيل تفاصيل طلب التورتة/التوصيل.
- يستقبل النظام الرسائل المتكررة بأمان عبر معرّف الرسالة الفريد، ويحافظ على فصل رسالة الموظف عن الملاحظة السرية.
- إيقاف الحساب أو إعادة كلمة المرور يبطل رموز الجلسات القديمة؛ ويعيد توجيه المحادثات المفتوحة عند تعطيل الموظف.
- إعداد KalemlyWA وQR للربط اليدوي، قائمة المنتجات بصورها وأسعارها وإرسال حتى 12 منتجًا معًا، مراحل الطلب بالجنيه المصري، صورة مرجعية للتورتة وأمر تحضير قابل للطباعة/الحفظ PDF.
- توجيه مبدئي تفاعلي حسب القسم، تقييم CSAT بعد الحل مع تنبيه فوري للتقييمات الأقل من 3، وخطاف تفريغ صوت اختياري.
- تطبيق ويب قابل للتثبيت مع Service Worker وإشعارات Push اختيارية؛ يلزم إعداد مفاتيح VAPID وإذن الإشعارات في المتصفح لتفعيل Push.

## ملاحظات نشر مهمة

### نشر Railway

أنشئ خدمات PostgreSQL وRedis، ثم خدمتي API وWeb من مجلدَي `apps/api` و`apps/web` (لكل منهما `railway.json`). اضبط API على `DATABASE_URL` و`REDIS_URL` من الخدمات المرتبطة، وولّد قيمًا قوية لـ `JWT_SECRET` و`KALEMLYWA_CONFIG_ENCRYPTION_KEY` و`KALEMLYWA_WEBHOOK_SECRET` و`MEDIA_SIGNING_SECRET`. اضبط `API_PUBLIC_URL` إلى عنوان HTTPS العام لخدمة API حتى يستطيع مزود القناة تحميل الوسائط. بعد النشر، انسخ رابط Webhook الكامل الذي تعرضه لوحة المدير إلى KalemlyWA؛ يحتوي الرابط رمز مصادقة مشتقًا ويجب عدم حذفه أو مشاركته علنًا. يمكن إدخال أسرار Meta وTelegram من إعدادات القنوات في لوحة المدير؛ وتظل متغيرات `META_*` و`TELEGRAM_*` بدائل اختيارية. عيّن `BONDOQ_ADMIN_PASSWORD` و`BONDOQ_AGENT_PASSWORD` قبل أول تشغيل إنتاجي؛ وإلا سيفشل seed بدل إنشاء كلمات مرور تجريبية معروفة. اضبط `WEB_ORIGIN` إلى نطاق Web، و`NEXT_PUBLIC_API_URL` إلى نطاق API أثناء بناء Web. سجّل `https://<api-domain>/webhooks/meta` لدى Meta؛ ويمكن للوحة Telegram تسجيل Webhook تلقائيًا.

هذا مشروع تأسيسي يحتاج مراجعة أمنية وتشغيلية قبل خدمة العملاء الفعلية. استخدم HTTPS، أسرارًا فريدة قوية، نسخًا احتياطيًا للبيانات، تخزينًا دائمًا مناسبًا، مراقبة للأخطاء، وسياسة احتفاظ للبيانات. واجهة المتصفح تحفظ JWT في `localStorage` لتسهيل النموذج؛ عند النشر المؤسسي استبدل ذلك بملفات تعريف ارتباط `HttpOnly` آمنة، وأضف تحديد المعدل، تدوير/إبطال الجلسات، وإدارة الأسرار. كما يلزم اختبار كل قناة بحساب Business حقيقي قبل الاعتماد.
